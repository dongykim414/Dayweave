# M2 Photo 구현 리포트

## 무엇을 만들었나

Today 기록에 선택적 사진 한 장을 추가하고, Native 앱 전용 저장소와 SQLite metadata로
재실행 후 복원할 수 있는 구조를 만들었습니다. 선택·교체·제거는 저장 버튼을 기준으로
확정되며 사진만 있는 Diary도 정상 기록입니다.

## 왜 DiaryEntry에 URI를 넣지 않았나

사진은 텍스트 기록과 수명주기와 저장 매체가 다릅니다. `DiaryPhoto`를 분리하면 binary는
file system에, 관계와 크기 같은 metadata는 SQLite에 둘 수 있고 향후 cloud sync에서도
photo ID를 안정적인 식별자로 사용할 수 있습니다. `diary_entry_id UNIQUE`는 현재 제품
규칙인 Diary당 최대 한 장을 DB에서도 보장합니다.

## 선택부터 저장까지

1. ImagePicker가 Gallery 권한을 요청하고 이미지 한 장을 받습니다.
2. ImageManipulator가 비율을 유지해 긴 변을 최대 1600px로 줄이고 JPEG 0.8로 저장합니다.
3. 이 결과는 저장 전까지 cache staging 파일이며 form preview에만 사용합니다.
4. 저장 시 UUID 이름으로 `documents/diary/photos/`에 복사합니다.
5. DiaryEntry와 DiaryPhoto metadata를 하나의 SQLite transaction으로 반영합니다.
6. 성공하면 staging과 교체 전 파일을 정리하고, 실패하면 새 persistent 파일을 보상
   삭제합니다.

파일 시스템과 SQLite는 하나의 atomic transaction이 될 수 없습니다. 그래서 기존 파일을
먼저 지우지 않고 `새 파일 준비 → DB 성공 → 기존 파일 정리` 순서를 선택했습니다. 이
순서의 핵심 장점은 DB 저장 실패가 기존 사용자의 사진 유실로 이어지지 않는다는 점입니다.

## Thumbnail을 별도로 만들지 않은 이유

MVP는 하루 한 기록·사진 한 장이며 Timeline도 한 달 범위만 읽습니다. display image 한
개를 작은 크기로 렌더링하면 충분해, thumbnail 파일까지 만들 때 생기는 저장 공간과
정리 복잡성을 피했습니다. 실제 M3 성능 측정에서 필요해질 때 별도 thumbnail migration을
추가할 수 있습니다.

## Web과 Native의 차이

Android/iOS는 SQLite와 documents file system을 사용합니다. Web localStorage에 base64를
저장하거나 picker의 임시 URI를 영구 URI처럼 취급하면 안정성과 용량 문제가 생기므로,
현재 Web preview에서는 사진 선택을 지원하지 않는다고 안내합니다. 텍스트 Diary Web
preview는 기존과 동일하게 유지됩니다.

## 직접 확인할 것

- 기존 v1 DB가 v2로 올라가면서 diary_entries가 유지되는지
- 사진만 저장 후 앱 재실행 시 사진이 보이는지
- 교체 후 `diary_photos`가 한 row이고 기존 파일이 삭제됐는지
- 제거 후 photo row와 파일이 모두 사라졌는지
- 권한 거부와 picker 취소에서 기존 form이 변하지 않는지

Native file/SQLite lifecycle은 JavaScript mock만으로 합격 처리하지 않습니다. 실제 Android
기기 또는 emulator에서 위 항목을 확인해야 M2를 완전히 닫을 수 있습니다.
