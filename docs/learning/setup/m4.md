# M4 Diary Detail 구현 리포트

## 무엇을 만들었나

Timeline Preview에서 stable Entry ID로 상세 화면을 열고 전체 Mood·사진·한 줄·긴 글을
확인할 수 있습니다. Edit mode에서는 Today와 같은 field와 validation으로 내용을
수정하며, 삭제는 확인 절차 뒤 DB와 사진을 정리합니다.

## 왜 날짜가 아니라 ID route인가

날짜는 현재 수정하지 않지만 미래에 이동이나 sync conflict가 생길 수 있습니다.
Entry ID는 저장된 객체의 정체성이므로 `/diary/[id]`가 더 안정적입니다. Repository의
`getRecordById`가 Diary와 Photo metadata를 함께 읽고 route 파일은 param만 전달합니다.

## 수정 때 새 row가 생기지 않는 이유

M1의 `buildDiaryEntry`에 기존 entry와 같은 날짜를 전달하면 `id`와 `createdAt`은 유지되고
`updatedAt`만 새로 생성됩니다. 실제 저장은 기존 `upsertRecord` transaction을 사용합니다.
모든 Mood·text·photo를 비운 경우 validation이 저장을 막고 삭제 동작을 안내합니다.

## Photo lifecycle을 공통화한 이유

Today와 Detail이 각각 file 순서를 구현하면 한쪽만 기존 파일을 먼저 지우는 회귀가 생길
수 있습니다. `saveDiaryRecord`가 두 화면의 순서를 다음처럼 통일합니다.

```text
prepared file 영구 저장
→ Diary + Photo metadata transaction
→ staging file 정리
→ 교체·제거된 기존 file 정리
```

DB가 실패하면 새 persistent file을 보상 삭제하고 기존 사진은 유지합니다. Edit를
취소하거나 저장하지 않고 나가면 새 prepared file만 정리합니다.

## 삭제 순서

Repository transaction 안에서 삭제할 record를 먼저 읽고 Diary row를 삭제합니다.
Photo metadata는 FK cascade로 삭제됩니다. 그 뒤 반환된 Photo URI의 파일을 삭제합니다.
이 순서는 DB 실패 때문에 사용자의 사진만 먼저 사라지는 상황을 막습니다. 반대로 DB는
성공하고 파일 삭제가 실패하면 orphan file이 남을 수 있으므로 오류를 기록하며, 자동
orphan sweep은 M4 범위를 넘어 후속 품질 과제로 남깁니다.

## 상태와 navigation

- Detail 저장 성공 시 hook의 record를 즉시 바꿔 View mode가 최신 내용을 표시합니다.
- 변경된 Edit를 취소하거나 back하면 Native Alert로 확인합니다.
- 삭제 성공은 `/timeline`으로 replace해 삭제된 상세로 다시 돌아가지 않게 합니다.
- Timeline은 M3의 focus reload로 visible month를 다시 읽어 stale marker를 제거합니다.

## 검토한 대안

- 날짜 route: 간단하지만 identity와 location이 결합되어 ID route를 선택
- 전역 state/cache: 두 화면의 focus reload로 충분해 dependency를 추가하지 않음
- 파일 먼저 삭제: DB 실패 시 복구 불가능해 제외
- TodayScreen 전체 재사용: 화면 목적이 달라 field와 lifecycle만 공통화
- custom modal: Native Alert로 충분해 새 UI 체계를 만들지 않음

## 직접 확인하는 방법

```bash
pnpm test
pnpm lint
pnpm typecheck
pnpm build:web
```

자동 테스트는 ID 조회·metadata 삭제, update identity, 빈 record validation, dirty state,
사진 교체 보상과 삭제 순서를 확인합니다. 실제 picker·SQLite cascade·파일 개수·Android
back/keyboard는 실제 기기나 emulator에서 확인해야 합니다.

현재 자동 검증은 11 suites/40 tests, Web 12개 static route와 Android JavaScript 1,315개
module bundle을 통과했습니다. Android export는 Windows에서 `--no-bytecode`로 확인한
JavaScript bundle이며 실제 Native 실행을 대체하지 않습니다.
