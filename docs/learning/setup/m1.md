# M1 Diary Core 구현 리포트

## 1. 이번 단계가 만든 결과

M0가 실행 가능한 앱 셸과 디자인·아키텍처 규칙을 만들었다면, M1은 처음으로
사용자 데이터를 기기에 보존하는 제품 흐름을 만들었습니다.

```text
앱 실행
  → Today
  → 감정 선택
  → 50자 한 줄
  → 필요하면 자세히 쓰기
  → 저장
  → 같은 날짜에는 새 row 대신 update
  → 앱 재실행 후 SQLite에서 복원
```

사진, Timeline, 삭제, 로그인, cloud와 AI는 이 흐름의 완료에 필요하지 않으므로
구현하지 않았습니다.

## 2. 책임을 어떻게 나눴는가

```text
TodayScreen                 화면 조립과 상태 표시
  ├─ MoodSelector           Mood 표현과 선택 callback
  ├─ QuickDiaryInput        50자 입력과 글자 수
  └─ LongDiaryInput         선택적 긴 글 접기/펼치기
            ↓
useTodayDiary               load, form, save와 feedback
            ↓
DiaryRepository             feature가 소유한 저장 계약
            ↓
SQLiteDiaryRepository       SQL과 row/domain mapping
            ↓
dayweave.db                 local persistent database
```

화면에서 SQL을 직접 호출하면 저장 기술을 바꾸거나 domain 규칙을 테스트하기
어렵습니다. Repository interface를 feature 경계에 두고 SQLite 구현을 data 계층에 둔
이유입니다.

## 3. DiaryEntry 최종 모델

```ts
interface DiaryEntry {
  id: string;
  entryDate: string;
  moodId: MoodId | null;
  shortText: string;
  content: string;
  createdAt: string;
  updatedAt: string;
}
```

- `entryDate`: device의 local calendar date를 `YYYY-MM-DD`로 표현
- `createdAt`, `updatedAt`: UTC ISO timestamp
- `moodId`: 의미만 저장하고 emoji·image path는 저장하지 않음
- `shortText`, `content`: 저장 직전에 trim하며 둘 다 빈 값일 수 있음

Mood, shortText, content가 모두 비어 있는 경우만 저장을 거부합니다. 그래서 사용자는
감정만, 한 줄만, 또는 감정과 긴 글을 원하는 수준으로 남길 수 있습니다.

## 4. 날짜와 timestamp를 분리한 이유

`new Date().toISOString().slice(0, 10)`으로 오늘을 만들면 UTC 날짜가 됩니다. 한국의
자정 전후처럼 UTC와 local date가 다른 시간에는 기록이 전날 또는 다음 날로 밀릴 수
있습니다.

M1은 `getFullYear`, `getMonth`, `getDate`로 device local date key를 만들고, 사건의
정확한 시각은 별도 UTC timestamp로 저장합니다. 날짜 utility는 윤년과 형식 검사를
포함한 unit test로 보호합니다.

## 5. 하루 한 기록을 두 층에서 지키는 방법

첫째, use-case는 같은 날짜의 기존 Entry가 있으면 `id`와 `createdAt`을 보존하고 내용과
`updatedAt`만 바꿉니다.

둘째, database는 `entry_date TEXT NOT NULL UNIQUE` constraint를 가집니다. 두 저장
요청이 경쟁하더라도 `ON CONFLICT(entry_date) DO UPDATE`가 같은 날짜에 두 row가 생기는
것을 막습니다. UI의 disabled 상태와 ref guard는 duplicate tap을 줄이고, DB constraint는
최종 데이터 무결성을 보장합니다.

## 6. Mood와 표현 자산 분리

Diary에는 `happy | calm | neutral | sad | stressed`만 저장합니다. Default Mood Pack은
각 ID를 한국어 label과 emoji에 연결합니다.

```text
Diary moodId "happy"
       ↓
moodPackRegistry["default"]
       ↓
{ label: "행복해요", visual: { type: "text", value: "😊" } }
```

나중에 Cat Pack이 이미지를 사용해도 과거 Diary 데이터는 바뀌지 않습니다. M1의
`MoodVisual`은 text와 image를 수용하지만 ownership이나 Pack 선택은 미리 구현하지
않았습니다.

## 7. SQLiteProvider를 선택한 이유

Expo SDK 57 공식 문서는 `SQLiteProvider`, `onInit`, `useSQLiteContext`와 async query
API를 제공합니다. root에서 Provider가 migration을 마친 뒤 children을 render하므로
Today가 table 생성보다 먼저 query하는 race condition을 피할 수 있습니다.

검토한 대안:

- module import 시 `openDatabaseSync`: 초기화 오류가 React 경계 밖에서 발생하고 UI를
  막을 수 있어 선택하지 않음
- 화면에서 `CREATE TABLE IF NOT EXISTS`: migration history가 없어 version 2 이후 schema 변경을
  관리하기 어려워 선택하지 않음
- ORM 추가: M1의 table 하나에는 추상화와 dependency 비용이 더 커서 선택하지 않음

## 8. Migration 전략

현재 `PRAGMA user_version`은 1입니다.

1. database open
2. WAL과 foreign key 활성화
3. `user_version` 조회
4. version 0이면 transaction에서 `diary_entries` 생성
5. 성공한 transaction에서 version 1 기록
6. 앱이 지원하는 version보다 DB가 새로우면 명시적으로 실패

다음 schema 변경은 `currentVersion === 1` 분기를 추가하고 version 2로 올리는 방식으로
확장합니다. migration 오류는 숨기지 않고 Provider까지 전파합니다.

## 9. Row와 Domain mapping

SQLite는 `entry_date`, `mood_id` 같은 snake_case를 사용하고 TypeScript는 `entryDate`,
`moodId`를 사용합니다. mapper 한 곳에서만 변환해 UI에 DB column 이름이 새지 않게
했습니다. DB에서 알 수 없는 Mood ID나 잘못된 날짜가 나오면 조용히 오염된 데이터를
사용하지 않고 오류로 드러냅니다.

## 10. ID 생성 선택

`Date.now()`는 같은 millisecond 충돌 가능성이 있고 cloud sync에서 기기 간 식별자로
부족합니다. Expo SDK 57에서 공식 지원하는 `expo-crypto`의 UUID v4를 사용했습니다.
이 기능 때문에 `expo-crypto`가 추가됐으며 범용 utility package는 추가하지 않았습니다.

## 11. 상태와 사용자 feedback

- DB 초기화: Suspense fallback
- Today 조회: loading 화면으로 빈 form flash 방지
- 저장: button disable과 `savingRef`로 중복 tap 방지
- 성공: modal 대신 inline “오늘의 기록을 남겼어요.”
- 실패: 사용자는 짧은 안내를 보고 개발자는 private text를 포함하지 않는 error log로
  원인을 확인
- 복원: 조회된 mood, shortText, content를 hook의 form state에 함께 반영

## 12. 테스트 전략

Expo가 공식 권장하는 Jest와 `jest-expo`를 사용합니다. Native SQLite를 대량 mock하면
실제 persistence를 검증한 것처럼 보일 수 있으므로 M1 자동 테스트는 순수 규칙에
집중합니다.

- Mood Registry resolution
- local date 생성과 유효성
- whitespace와 50자 validation
- create/update 시 ID와 createdAt 보존
- DB row와 Domain mapping 및 오염 값 거부

실제 migration과 앱 재실행 persistence는 Android/iOS 기기 또는 emulator에서 별도로
확인해야 합니다.

## 13. Dependency 선택

- `expo-sqlite ~57.0.2`: Expo 공식 persistent SQLite와 Provider lifecycle
- `expo-crypto ~57.0.2`: 공식 UUID v4
- `jest`, `jest-expo`, `@types/jest`, `@react-native/jest-preset`: Expo/RN 0.86에 맞는
  최소 unit test 구성

Zustand, TanStack Query, ORM, date library와 cloud dependency는 추가하지 않았습니다.

## 14. 구현 중 실패에서 배운 점

임시 `.npmrc`가 `store-dir`에 `v11`을 중복 지정해 기존 `node_modules`가 잘못된 store에
연결됐습니다. 파일을 취소한 뒤 pnpm이 store 불일치를 정확히 차단했습니다. 생성물
폴더를 휴지통으로 보내고 lockfile로 재설치해 정상 store를 복구했습니다.

또한 sandbox는 Expo cache와 일부 postinstall 하위 프로세스를 `EPERM`으로 막을 수
있습니다. 이 환경 제약과 dependency 결함을 구분하기 위해 frozen install, peer 검사,
GitHub CI 결과를 함께 사용합니다.

## 15. 수동 Acceptance 상태

| Case | 상태 | 근거 |
| --- | --- | --- |
| 1. 새 기록 저장 | NOT TESTED | Android/iOS 기기 없음 |
| 2. 앱 재실행 후 복원 | NOT TESTED | 실제 native lifecycle 필요 |
| 3. 기존 기록 수정 | NOT TESTED | 자동 test로 ID·createdAt 보존은 확인, native 수동 실행은 하지 못함 |
| 4. 긴 글 포함 복원 | NOT TESTED | 실제 native persistence 필요 |
| 5. 모두 빈 값 저장 거부 | NOT TESTED | 자동 validation test는 통과, native UI 수동 실행은 하지 못함 |
| 6. 같은 날짜 row 하나 | NOT TESTED | DB unique/upsert 구현, 실제 DB inspector 확인 필요 |

Web static export는 성공했지만 실제 기기 persistence를 대신하지 않습니다.

추가로 Expo Web 개발 서버의 `/today` 요청에서는 SQLite `worker.ts` chunk를 찾지 못하는
오류가 관찰됐습니다. Expo SQLite의 Web 지원은 공식 문서에서도 alpha이며 WASM과
COOP/COEP 설정이 필요합니다. M1은 모바일 앱의 native SQLite를 완료 기준으로 유지하고,
Web persistence는 별도 호환성 작업으로 분리합니다.

## 16. 다음 단계 전 확인

M2를 시작하기 전 Android 또는 iOS에서 Case 1, 2, 4, 6을 실행하고 SQLite inspector로
같은 날짜 row가 하나인지 확인하는 것이 가장 중요합니다. 이 검증이 끝나기 전까지
“M1 코드 구현 완료”와 “M1 제품 검증 완료”를 구분해야 합니다.
