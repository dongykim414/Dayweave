# M0 Foundation

이 문서는 Dayweave의 M0 Foundation 단계에서 결정한 핵심 원칙을 한 문서로 압축한 요약입니다.

M0는 최종 앱을 완성하는 단계가 아니라, 이후 M1, M2, M3가 안전하게 쌓일 수 있는 기반을 만드는 단계입니다. 즉, 지금 이 문서는 “기획이 아니라 구조를 세우는 문서”로 이해하는 게 가장 중요합니다.

## 빠르게 보는 목차

- 제품 방향과 범위
- app / feature / shared 구조
- 테마와 shared UI 원칙
- Mood와 Avatar의 도메인 경계
- pnpm, Node, npm의 차이
- CI와 검증 규칙
- review와 merge 전략
- AI 작업을 위한 harness 원칙

## 실제 코드 구조와의 연결

이 문서는 추상 원칙만 설명하는 문서가 아니라, 실제 프로젝트 구조와 연결됩니다.

- app/
  - 라우팅과 화면 조립을 담당
  - 예: 라우트 파일, 레이아웃, 탭 구조
  - 이 문서의 “앱 구조” 원칙과 맞닿아 있음

- src/features/
  - 기능 단위의 화면, 로직, 상태를 관리
  - 예: diary, mood, avatar 같은 도메인 영역
  - 이 문서의 “책임 분리” 원칙과 맞닿아 있음

- src/shared/
  - 재사용 가능한 UI primitive
  - AppText, AppButton, AppCard, AppScreen, AppIconButton 등
  - 이 문서의 “테마와 shared UI” 원칙과 맞닿아 있음

- .github/workflows/
  - PR 검증과 release 자동화
  - 이 문서의 “CI와 검증” 원칙과 맞닿아 있음

- docs/
  - 제품 방향과 학습 기록을 보관
  - 이 문서의 “범위 통제”와 “학습 문서화” 원칙과 맞닿아 있음

이 문서의 각 섹션은 실제 코드를 어떻게 나누어야 하는지, 어떤 규칙을 따라야 하는지를 설명하는 지도 역할을 합니다.

## 1. 제품 방향과 범위

Dayweave는 감정과 한 줄, 선택적 사진으로 하루를 빠르게 남기고 필요할 때 긴 글로 확장하는 개인 모바일 다이어리입니다.

핵심은 다음과 같습니다.

- 하루의 경험을 10~30초 안에 기록한다.
- 기본 흐름은 감정 + 한 줄 + 선택적 사진이다.
- 긴 글은 선택적 확장이다.
- 현재는 기록의 핵심 경험을 만들고, 이후 기능을 단계적으로 추가한다.

그래서 M0는 실제 다이어리 CRUD를 한 번에 끝내는 단계가 아니라, 이후 기능을 안전하게 쌓을 수 있는 구조를 만드는 단계입니다.

### 범위 통제의 원칙

- 미래 비전은 문서로 남긴다.
- 지금 구현 범위는 명시적으로 제한한다.
- 다른 제품 방향(예: 일정/Todo 앱)을 현재 코드에 섞지 않는다.

이것이 범위 통제입니다. 오래된 기획 문서는 제거하고, 현재 기준 문서 하나만 남기는 것이 맞습니다.

## 2. 구조와 책임 분리

구조는 다음과 같이 나뉩니다.

- app/
  - 경로와 화면 연결
  - 라우팅, 레이아웃, 네비게이션 배치
  - 비즈니스 로직을 담지 않는다.

- src/features/
  - 각 제품 관심사별 기능 영역
  - diary, mood, avatar, theme, profile 등
  - 기능 로직과 사용자 경험 규칙을 담는다.

- src/shared/
  - 공용 UI primitive
  - AppText, AppButton, AppCard, AppScreen, AppIconButton
  - 특정 기능을 몰라야 하며, 재사용성이 높은 공용 도구여야 한다.

### 핵심 규칙

- app은 배치와 연결만 담당한다.
- feature는 기능의 의미와 로직을 담당한다.
- shared는 기능에 종속되지 않는 도구다.

이 경계가 흐트러지면 재사용성과 유지보수성이 크게 떨어집니다.

## 3. Theme과 shared UI

하드코딩된 HEX 값을 화면 곳곳에서 직접 쓰는 구조는 확장에 불리합니다.

예:

```tsx
backgroundColor: "#F6F4EF"
color: "#17201C"
```

이 방식은 테마가 늘어날수록 한 번에 바꾸기 어렵고, 의미를 이해하기 어렵습니다.

그래서 M0는 semantic token을 도입합니다.

```tsx
theme.colors.background
theme.colors.textPrimary
theme.colors.primary
theme.colors.danger
```

### 핵심 의도

- 색은 값 자체보다 역할로 표현한다.
- 화면 코드는 실제 색값을 알 필요가 없다.
- 새 테마를 추가할 때 화면 로직을 손대지 않아도 된다.

`ThemeProvider`는 앱 트리 상단에서 현재 테마를 제공하고, `useTheme()`는 하위 화면에서 token을 읽게 합니다.

이 구조는 다음과 같은 이점을 줍니다.

- 색 변경이 한 곳에서 가능
- 일관성 유지
- 테마 확장 가능
- UI 컴포넌트 재사용

## 4. Mood와 Avatar의 도메인 경계

사용자 데이터는 시각 표현 자산에 종속되면 안 됩니다.

다음처럼 image path를 저장하는 방식은 확장에 불리합니다.

```text
assets/cat-pack/happy-v2.png
```

실패 포인트는 다음과 같습니다.

- 자산 이름이 바뀌면 과거 기록을 해석하기 어렵다.
- Mood Pack이 바뀌면 기존 기록이 잘못 표현된다.
- UI와 데이터가 결합되어 확장이 힘들다.

그래서 M0는 semantic Mood ID를 사용합니다.

```ts
type MoodId = "happy" | "calm" | "neutral" | "sad" | "stressed";
```

기록에는 의미를 저장하고, 화면에서 현재 Mood Pack이 이를 이미지, 이모지, animation으로 해석합니다.

Avatar도 마찬가지입니다.

- 캐릭터 전체 이미지를 저장하지 않는다.
- body, hair, top, bottom, accessory 같은 파츠를 분리해서 저장한다.
- 표현 자산과 사용자 데이터가 분리된다.

이 구조는 나중에 Mood Pack, Theme Pack, Avatar item, Catalog/Ownership/Selection을 안전하게 추가할 수 있게 해줍니다.

## 5. shared UI는 기능 로직을 가져서는 안 된다

공용 UI는 도구처럼 동작해야 합니다.

예:

- AppText
- AppButton
- AppCard
- AppScreen
- AppIconButton

이들은 다음을 알아서는 안 됩니다.

- 저장 로직
- 로그인 여부
- SQLite table 이름
- Diary 저장 문구
- Mood 이미지 경로

공용 UI는 다음만 책임집니다.

- 형태
- 접근성
- 기본 동작
- 테마 토큰 적용
- 재사용 가능성

기능의 의미와 상태는 feature가 소유해야 합니다.

## 6. pnpm, Node, npm의 기본 이해

### Node.js

JavaScript를 브라우저 밖에서 실행할 수 있게 해주는 런타임입니다.

- React Native 앱 실행
- Expo dev server 실행
- build 도구 실행
- package 설치와 스크립트 처리

이런 작업을 가능하게 합니다.

### npm

Node 생태계의 기본 패키지 관리자입니다.

- dependency 설치
- script 실행
- lockfile 관리

### pnpm

npm과 같은 목적을 가지지만, 설치와 의존성 관리 방식을 더 효율적으로 설계한 도구입니다.

핵심 차이는 다음과 같습니다.

- 중복 설치를 줄인다.
- 저장 공간을 더 효율적으로 사용한다.
- lockfile 기반으로 재현 가능한 설치를 만든다.
- 프로젝트 간 dependency 구조를 더 깔끔하게 관리한다.

이 프로젝트는 pnpm을 사용하고 있으며, package.json에서 packageManager를 pnpm으로 지정합니다.

## 7. CI와 검증

GitHub Actions는 `.github/workflows/` 안의 yml 파일을 읽고 트리거에 맞춰 자동 실행합니다.

### pr-check.yml

PR 생성이나 main push 시 실행합니다.

검증 항목은 다음과 같습니다.

- `pnpm install --frozen-lockfile`
- `pnpm deps:check`
- `pnpm lint`
- `pnpm typecheck`
- `pnpm build:web`

이 검증은 다음을 확인합니다.

- 의존성이 Expo와 잘 맞는지
- 코드 스타일이나 잠재적 문제를 잡는지
- TypeScript 계약을 지키는지
- Web export가 가능한지

### release-cut.yml

매주 수요일 정해진 시간에 release 브랜치를 자동으로 생성합니다.

현재 형식은 다음과 같습니다.

```bash
branch_name="release/$(date -u +'%G-W%V')"
```

즉, 현재 정책은 release/YYYY-Www 형태로 주차 기반 release 브랜치를 생성하는 방식입니다.

## 8. 적절한 리뷰와 merge 전략

이 프로젝트는 stacked PR 구조를 사용합니다.

- PR #1: Expo migration
- PR #2: M0 Foundation

이렇게 분리하는 이유는 다음과 같습니다.

- 논리적 변경 단위를 나눈다.
- 리뷰 범위를 작게 유지한다.
- base branch 전환과 rebase를 관리할 수 있다.

PR #2가 PR #1 위에서 시작된 경우, PR #1이 merge된 뒤 main 기준으로 rebase하고 base를 main으로 바꾸는 방식이 맞습니다.

핵심 포인트는 다음과 같습니다.

- main에서 branch를 만들고, 서로 독립적으로 작업하기
- merge 순서를 관리하기
- rebase 후 force-with-lease로 안전하게 push하기
- 리뷰와 병합을 작은 단위로 나누기

## 9. AI 작업 관찰과 harness

AI를 안전하게 쓰려면 단순히 “프롬프트를 잘 쓰는 것”만으로 부족합니다.

필요한 것은 다음입니다.

- 제품 범위 문서
- 현재 작업 범위와 제외 범위
- 파일 구조와 규칙
- 검증 명령
- 실패를 관찰 가능한 사실로 기록
- 추론과 사실을 분리

이것이 harness engineering의 핵심입니다.

## 10. M0가 만든 기본 설계

M0의 최종 목표는 “시작 가능한 구조”를 만드는 것입니다.

- product direction 정리
- route와 feature 분리
- theme과 shared UI 계층화
- mood/avatar 의미 데이터 분리
- pnpm + CI 설치
- 검증과 리뷰 기준 정리

이 과정이 완료되어야 이후 M1, M2에서 diary CRUD, 사진 기능, 저장소, 사용자 설정, 커스터마이징 등을 안전하게 붙일 수 있습니다.

## 11. 핵심 정리

M0는 사용자가 실제 일기를 저장하는 버전이 아니라, 앞으로 일기 기능을 안전하게 쌓을 수 있도록 기반을 세우는 단계입니다.

이 단계에서 가장 중요한 원칙은 다음 4가지입니다.

1. 범위를 통제한다.
2. 책임을 분리한다.
3. 시각 규칙을 테마로 통일한다.
4. 의미와 표현을 분리한다.

이 원칙이 지켜지면 이후 기능이 추가될 때 구조가 무너지지 않고, 작업이 점점 더 안전해집니다.
