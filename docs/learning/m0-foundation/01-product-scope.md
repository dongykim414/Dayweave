# 01. 제품 방향과 범위

## 이번 작업에서 발견한 문제

저장소의 기존 README와 `docs/product/mvp.md`는 Dayweave를 일정·Todo 앱으로
설명했습니다. 반면 이번 M0 요청과 제품·기술 설계서는 다음 제품을 설명했습니다.

> 감정 + 한 줄 + 선택적 사진으로 빠르게 기록하고, 원할 때 긴 글로 확장하는 개인
> 다이어리

두 설명을 그대로 함께 두면 사람과 AI가 서로 다른 제품을 만들게 됩니다. 예를 들어
“Today 화면을 구현해 줘”라는 요청을 받았을 때 한쪽은 오늘 일정표를, 다른 쪽은 오늘
감정 기록 화면을 만들 수 있습니다.

이 문제는 단순 문구 오류가 아닙니다. 제품 정의가 다르면 데이터 모델, 화면 구조,
테스트와 로드맵이 모두 달라집니다.

## 선택한 방법

`docs/PRODUCT.md`를 현재 제품 범위의 단일 기준 문서로 만들었습니다.

- README: 프로젝트를 처음 보는 사람을 위한 짧은 소개
- `docs/PRODUCT.md`: 현재 제품 원칙, MVP, M0 포함·제외 범위
- `docs/ROADMAP.md`: 어느 마일스톤에서 무엇을 구현할지 설명
- `docs/product/mvp.md`: 예전 링크가 끊기지 않도록 새 문서 위치를 알리는 안내

여기서 중요한 표현은 **단일 기준**입니다. 같은 요구사항을 여러 파일에 자세히 복사하면
수정 시 한 파일만 바뀌어 다시 충돌합니다. 다른 문서는 `docs/PRODUCT.md`를 가리키고,
제품 범위의 최종 판단은 한 곳에서 하도록 했습니다.

## M0와 제품 MVP는 다르다

### M0 Foundation

개발을 시작할 수 있는 구조와 규칙을 만드는 단계입니다.

- 4탭 navigation
- ThemeProvider와 Sky Theme
- 공용 UI
- Mood와 Avatar의 타입 경계
- 문서와 검증 명령

M0 완료 후에도 사용자는 실제 일기를 저장할 수 없습니다.

### 제품 MVP

사용자가 핵심 가치를 경험할 수 있는 최소 제품입니다.

- 감정 + 한 줄 + 선택 사진 기록
- 필요할 때 긴 글 추가
- 저장, 조회, 수정, 삭제
- 날짜별 타임라인
- 기본 개인화 기능

즉 M0는 제품 MVP를 구성하는 첫 번째 기술 마일스톤입니다. “M0가 끝났다”와
“MVP가 끝났다”를 혼용하면 일정과 품질 기대치가 크게 어긋납니다.

## 왜 CRUD부터 만들지 않았는가?

CRUD부터 만드는 것도 가능합니다. 하지만 현재는 다음 결정이 먼저 필요했습니다.

- 기록이 어떤 제품 철학을 따르는가?
- 화면 코드는 어디에 놓는가?
- 색상과 공용 UI는 어떤 방식으로 재사용하는가?
- 감정 데이터와 감정 이미지를 어떻게 분리하는가?
- AI가 범위 밖 기능을 추가하지 않도록 무엇으로 통제하는가?

이 경계 없이 CRUD를 먼저 만들면 기능은 빨리 보이지만, M1~M4에서 폴더 이동,
스타일 교체, 데이터 마이그레이션을 반복할 가능성이 큽니다. M0는 모든 미래를 설계한
것이 아니라, 가까운 마일스톤에서 반복될 핵심 경계만 먼저 고정한 것입니다.

## 고려한 다른 선택지

### 선택지 A: 기존 일정/Todo 방향을 유지한다

장점은 기존 README와 화면을 거의 수정하지 않아도 된다는 점입니다. 하지만 이번 기준
문서와 핵심 사용자 경험이 완전히 달라 요구사항을 충족하지 못합니다.

### 선택지 B: 일정 앱과 다이어리를 동시에 MVP에 넣는다

장기 비전에는 일정·SNS 연결이 있으므로 자연스러워 보일 수 있습니다. 하지만 초기
사용자 문제, 데이터 모델과 화면 수가 동시에 늘어 핵심 기록 경험을 검증하기 어렵습니다.
따라서 일정 연결은 장기 방향으로 문서에 남기고 코드에서는 제외했습니다.

### 선택지 C: 예전 `docs/product/mvp.md`를 삭제한다

문서 중복은 줄지만 과거 PR, 대화, 북마크의 링크가 끊깁니다. 그래서 내용을 유지하지는
않되 새 기준 문서로 연결하는 migration 안내로 남겼습니다.

### 선택지 D: 모든 미래 기능의 interface를 M0에 만든다

확장 가능해 보이지만 실제 요구가 없는 abstraction은 잘못된 형태로 굳을 수 있습니다.
M0에서는 Theme, Mood, Avatar처럼 기준 문서가 명확히 요구한 경계만 타입으로 만들고,
Repository·Catalog·결제 interface는 실제 구현 마일스톤까지 미뤘습니다.

## 이 결정의 비용

- 기존 일정/Todo 시안을 그대로 재사용하지 못합니다.
- 실제 사용자 기능이 보이기까지 한 단계가 더 필요합니다.
- 제품 방향이 다시 바뀌면 canonical 문서와 구조를 함께 갱신해야 합니다.

그 대신 개발자와 AI가 같은 제품을 바라보고, 범위 밖 기능이 조용히 섞이는 위험을
줄였습니다.
